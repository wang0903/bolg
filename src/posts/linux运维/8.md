# Ubuntu 24.04.3 服务器登录卡顿（20秒+）完整排查与解决指南

## 问题现象

- 输入密码后等待 20+ 秒才能进入 Shell
- `systemctl status systemd-resolved` 报错 `Connection timed out` 或 `Failed to connect to bus`
- `reboot`、`shutdown` 等命令失效

------

## 根本原因

**`systemd-resolved` 服务卡死/假死**，导致：

1. D-Bus 系统总线被阻塞
2. 用户会话启动时等待 DNS 解析超时
3. 最终连锁反应导致 systemd 通信通道崩溃

------

## 完整解决步骤

### 阶段一：强制终止卡死的 resolved 进程

bash

```
# 1. 强制终止 systemd-resolved（注意用 -f 匹配完整命令行）
sudo pkill -9 -f systemd-resolved

# 2. 或者用 killall（更简单）
sudo killall -9 systemd-resolved
```



------

### 阶段二：清理残留文件（解决 D-Bus 阻塞）

bash

```
# 1. 删除 resolved 的状态目录和 socket 文件
sudo rm -rf /run/systemd/resolve/
sudo rm -f /run/systemd/units/*
sudo rm -f /run/dbus/system_bus_socket

# 2. 强制重启 D-Bus 守护进程
sudo killall -9 dbus-daemon
sudo /usr/bin/dbus-daemon --system --fork
```



------

### 阶段三：文件系统级禁用 resolved（绕过 systemctl）

>  此时 `systemctl` 可能仍不可用，直接在文件系统层面操作

bash

```
# 1. 删除 resolved 的所有开机启动软链接
sudo rm -f /etc/systemd/system/multi-user.target.wants/systemd-resolved.service
sudo rm -f /etc/systemd/system/sysinit.target.wants/systemd-resolved.service
sudo rm -f /etc/systemd/system/dbus-org.freedesktop.resolve1.service
sudo rm -f /lib/systemd/system/systemd-resolved.service

# 2. 创建 mask 文件（彻底屏蔽，即使以后 systemctl 恢复也不会启动）
sudo mkdir -p /etc/systemd/system
sudo ln -sf /dev/null /etc/systemd/system/systemd-resolved.service
```



------

### 阶段四：切换为传统 DNS 解析方式

bash

```
# 1. 删除 systemd-resolved 管理的软链接 resolv.conf
sudo rm -f /etc/resolv.conf

# 2. 创建传统 resolv.conf，写入可靠的 DNS 服务器
echo "nameserver 223.5.5.5" | sudo tee /etc/resolv.conf
echo "nameserver 223.6.6.6" | sudo tee -a /etc/resolv.conf

# 3. 锁定 resolv.conf，防止被其他服务（如 NetworkManager）覆盖
sudo chattr +i /etc/resolv.conf
```



> DNS 服务器说明：
>
> - `223.5.5.5` / `223.6.6.6` = 阿里云公共 DNS（国内推荐）
> - `114.114.114.114` / `114.114.115.115` = 114DNS（备选）
> - `8.8.8.8` / `1.1.1.1` = Google/Cloudflare（如果服务器能访问外网）

------

### 阶段五：强制重启系统

由于 systemd 通信已崩溃，`reboot` 和 `shutdown` 命令均无法使用，只能用 SysRq 强制重启：

bash

```
# 1. 同步磁盘缓存（防止数据丢失）
echo s | sudo tee /proc/sysrq-trigger

# 2. 等待 2-3 秒
sleep 3

# 3. 强制重启
echo b | sudo tee /proc/sysrq-trigger
```



> 如果 SysRq 也不响应，直接去物理机按重启键，或在云服务商控制台点击"强制重启"

------

### 阶段六：重启后验证

bash

```
# 1. 确认 resolved 没有运行
ps aux | grep resolved | grep -v grep
# 应该没有任何输出

# 2. 确认 DNS 解析正常
ping -c 3 223.5.5.5
ping -c 3 baidu.com
# 两个都应该通

# 3. 确认 resolv.conf 内容正确
cat /etc/resolv.conf
# 应该显示:
# nameserver 223.5.5.5
# nameserver 223.6.6.6

# 4. 确认 systemctl 已恢复正常
sudo systemctl status sshd
# 应该正常显示服务状态

# 5. 最终测试：退出 SSH 重新登录，感受登录速度
exit
# 重新 SSH 连接，输入密码后应该秒进
```



------

##  附录一：如果重启后 resolved 又出现了

执行以下命令彻底禁用（这次 systemctl 应该能用了）：

bash

```
sudo systemctl stop systemd-resolved
sudo systemctl disable systemd-resolved
sudo systemctl mask systemd-resolved
sudo rm -f /etc/resolv.conf
echo "nameserver 223.5.5.5" | sudo tee /etc/resolv.conf
echo "nameserver 223.6.6.6" | sudo tee -a /etc/resolv.conf
sudo chattr +i /etc/resolv.conf
```



------

## 附录二：如何用 systemd-analyze 提前预警

如果以后想提前发现潜在问题，可以定期检查：

bash

```
# 查看系统启动耗时最长的服务
systemd-analyze blame

# 查看用户会话启动耗时
systemd-analyze --user blame

# 查看 resolved 服务日志是否有大量 timeout
sudo journalctl -u systemd-resolved -n 50 --no-pager | grep -i timeout
```



如果某个服务（如 `systemd-networkd-wait-online.service`）耗时超过 10 秒，可以考虑禁用：

bash

```
sudo systemctl disable systemd-networkd-wait-online.service
```



------

##  附录三：为什么选择禁用 resolved 而不是修复？

- `systemd-resolved` 在 Ubuntu 24.04 上确实存在一些稳定性问题（尤其是在网络环境复杂或 DNS 响应慢时）
- 对于服务器来说，传统的 `/etc/resolv.conf` 方式更加稳定可靠，性能更好
- 禁用 resolved 不会影响系统正常功能，只是将 DNS 解析交给 glibc 的 `getaddrinfo` 直接处理
